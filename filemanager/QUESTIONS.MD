# Контрольные вопросы — Практическая работа «Работа с файлами в PHP»

## 1. Зачем добавлять папку PHP в переменную PATH и как проверить, что PHP установлен?

Добавление папки PHP (например, C:\php) в переменную среды PATH позволяет вызывать команду php из любого окна CMD и из любой папки, не указывая каждый раз полный путь к php.exe. Без этого пришлось бы писать C:\php\php.exe -v вместо короткого php -v.

Проверить установку можно двумя командами:

php -v       — выведет версию PHP (например, PHP 8.3.x)
php --ini    — покажет путь к загруженному php.ini

Если строка Loaded Configuration File показывает (none), значит PHP не нашёл файл php.ini — нужно проверить, что он лежит рядом с php.exe и назван без расширения .txt.

## 2. Какой командой запускается встроенный сервер PHP и как указать другой порт или корневую папку?

Встроенный сервер запускается командой:

php -S localhost:8000

Другой порт (если 8000 занят):

php -S localhost:8080

Запуск с указанием корневой папки (из любого места):

php -S localhost:8000 -t C:\projects\filemanager

Сайт доступен с других компьютеров локальной сети:

php -S 0.0.0.0:8000

Временная замена настроек php.ini только для одного запуска:

php -d upload_max_filesize=20M -d post_max_size=25M -S localhost:8000

Запуск со своим файлом php.ini:

php -S localhost:8000 -c C:\projects\filemanager\php.ini

## 3. Почему форма загрузки не работает без enctype="multipart/form-data"?

Атрибут enctype определяет способ кодирования данных формы при отправке на сервер. По умолчанию используется application/x-www-form-urlencoded, при котором поля кодируются как строка name=value&..., и файлы таким способом передать нельзя — они слишком велики и содержат двоичные данные.

Значение multipart/form-data разбивает тело запроса на части (multipart), каждая из которых может содержать либо обычное поле, либо файл целиком. Только при таком кодировании PHP помещает принятый файл во временную папку и заполняет массив $_FILES. Без этого атрибута массив $_FILES будет пустым, а файл просто не будет передан.

## 4. Какие ключи содержит массив $_FILES['userfile'] и что хранится в tmp_name?

Массив $_FILES['userfile'] содержит следующие ключи:

- name — исходное имя файла, как его прислал браузер;
- full_path — полный путь (в современных версиях PHP обычно совпадает с name);
- type — MIME-тип, присланный браузером (например, application/pdf);
- tmp_name — **временный путь** к файлу на сервере (например, C:\Windows\Temp\php1A2B.tmp);
- error — код ошибки загрузки (0 = успешно);
- size — размер файла в байтах.

В tmp_name хранится путь к временному файлу, который PHP автоматически создал в системной папке временных файлов. Этот файл удаляется сразу после окончания скрипта, поэтому его нужно успеть переместить в постоянное хранилище функцией move_uploaded_file().

## 5. Чем move_uploaded_file() отличается от copy()?

- copy($src, $dst) — копирует любой файл по любым путям. Не проверяет, откуда файл взялся.
- move_uploaded_file($tmp_name, $destination) — проверяет, что файл в $tmp_name действительно был загружен через HTTP-форму (то есть что он присутствует в массиве $_FILES). Если это не так, функция откажется его перемещать.

Для загрузок используют именно move_uploaded_file(), потому что она защищает от подмены: злоумышленник не сможет подсунуть скрипту путь к системному файлу (например, C:\Windows\system32\config\SAM) и заставить его скопировать этот файл в открытую папку.

## 6. Чем отличаются директивы upload_max_filesize и post_max_size? Какое значение должно быть больше и почему?

- upload_max_filesize` — максимальный размер **одного** загружаемого файла.
- post_max_size` — максимальный размер **всего** POST-запроса целиком, то есть сумма размеров всех файлов и всех текстовых полей формы.

post_max_size должно быть **больше** upload_max_filesize, потому что в один POST-запрос может входить несколько файлов плюс обычные поля формы. Если бы post_max_size был меньше, то форма с одним файлом «вписалась» бы в upload_max_filesize, но весь запрос превысил бы post_max_size, и PHP молча отбросил бы всё целиком (массивы $_POST и $_FILES остались бы пустыми).

Правило соотношения: memory_limit ≥ post_max_size > upload_max_filesize.

## 7. Что произойдёт с массивами $_POST и $_FILES, если запрос больше post_max_size?

При превышении post_max_size PHP не обрабатывает тело запроса: массивы $_POST и $_FILES остаются **полностью пустыми**. Обычная проверка $_FILES['userfile']['error'] не сработает, потому что самого элемента нет.

Признак превышения — пустой $_FILES при ненулевой длине тела запроса (заголовок CONTENT_LENGTH больше нуля):

if ($_SERVER['REQUEST_METHOD'] === 'POST'
    && empty($_FILES)
    && ($_SERVER['CONTENT_LENGTH'] ?? 0) > 0) {
    die('Запрос больше post_max_size (' . ini_get('post_max_size') . ')');
}

## 8. Почему upload_max_filesize нельзя изменить через ini_set()?

Параметр upload_max_filesize проверяется на этапе приёма HTTP-запроса, **до** того, как PHP запустит скрипт. К моменту вызова ini_set() файл уже либо принят, либо отвергнут сервером — изменять настройку поздно.

Эти директивы задают только в php.ini или через ключ -d при запуске PHP:

php -d upload_max_filesize=20M -d post_max_size=25M -S localhost:8000

Через ini_set() можно менять только те параметры, которые вступают в силу во время работы скрипта: memory_limit и max_execution_tim.

## 9. Для чего при удалении и сохранении файлов используется basename()`?

Функция basename($path) возвращает только имя файла, отбрасывая любой путь. Это нужно для безопасности — чтобы имя файла, пришедшее от пользователя, не содержало конструкций вроде ../.

Если в delete.php не применить basename(), злоумышленник может передать ?file=../index.php, и путь __DIR__ . '/uploads/' . '../index.php' укажет на файл сайта, а не на файл в папке uploads. Тогда unlink() удалит сам index.php и сломает сайт.

После basename('../index.php') останется просто index.php, и путь будет указывать внутрь uploads/, поэтому выйти из папки не получится.

## 10. Почему нельзя разрешать загрузку файлов с расширением .php?

Если разрешить загрузку .php и класть такие файлы в открытую папку uploads/, то при обращении к http://localhost:8000/uploads/malicious.php веб-сервер **выполнит** этот файл как PHP-скрипт. Злоумышленник сможет загрузить скрипт, который:

- читает и удаляет любые файлы на сервере;
- подключается к базе данных и крадёт данные;
- открывает обратный шелл и получает полный контроль над сервером;
- рассылает спам или участвует в DDoS-атаках.

Поэтому загрузку .php (а также .phtml, .phar, .htaccess) всегда запрещают списком разрешённых расширений, а не списком запрещённых: белый список безопаснее, потому что его нельзя обойти неожиданным расширением.
